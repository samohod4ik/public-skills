# Прямой выход для российских префиксов

Документ про профиль, у которого исходящий по умолчанию — proxy, а российские сети уходят мимо TUN. Профиль **Agents only** сюда не входит: там Tun routing остаётся выключенным, потому что process rules вместе с выключенным Strict Route дают петлю ([Throne #1365](https://github.com/throneproj/Throne/issues/1365)).

## Итог

Исключение из TUN строит только встроенное имя `geoip-ru` (и явные CIDR). Файл `.srs` по URL в это исключение не входит: он матчится уже внутри ядра, после того как пакет вошёл в `throne-tun`.

## Откуда берётся исключение

При включённом Tun Routing `src/configs/generate.cpp` (ветка `dev`, чтение 2026-11-05) копирует результат `get_direct_ips()` в `route_exclude_address` и `route_exclude_address_set`. `get_direct_ips()` оставляет имя rule-set, только если оно начинается с `geoip-`, и оставляет явные `ip_cidr`. URL на `https://` отбрасывается. Это `RouteProfile.cpp` той же ветки, строки 1025–1039, по двум независимым чтениям 2026-11-05. Повторная загрузка raw-URL в тот же день не удалась, поэтому номер строк здесь не перепроверялся локально.

Имя `geoip-ru` есть во встроенном списке Throne 1.3.2 и указывает на MetaCubeX `geo/geoip/ru.srs`. `geosite-ru` тоже есть. Он кормит DNS-правила, не таблицу маршрутов Windows.

Поле `GeoIP: ru` и исходящий узел с именем RoscomVPN относятся к другому клиенту. В Throne 1.3.2 правило пишется как `ruleset:geoip-ru` в простом списке или как имя `geoip-ru` в `rule_set`. Исходящий «через VPN» — это `proxy` (`-1`), уже запущенный узел.

## Колонка tls_spoof

В `route_rules.tls_spoof` хранится пустая строка. Целое `0` SQLite сохраняет текстом `0`. Ядро считает непустую строку включённым режимом и пишет `tls_spoof: open WinDivert: … WinDivert64.sys: The system cannot find the file specified`.

## Прогон 2026-11-05, Throne 1.3.2

Tun Routing уже был включён. Профиль перезагрузили, TUN остался включён. В прямое IP-правило добавлен `geoip-ru`. `tls_spoof` на правилах профиля — пустая строка.

| Проверка | Результат |
|----------|-----------|
| Маршруты IPv4 с next hop `172.19.0.2` | 31569 |
| `Find-NetRoute` для `77.88.44.55` | Ethernet, next hop `10.77.111.1` |
| `curl https://ya.ru` | HTTP 302 за 0,09 с, локальный адрес `10.77.111.236`, удалённый `77.88.55.242` |
| `curl https://webim.armgs.team` | HTTP 200 за 0,12 с, локальный адрес `10.77.111.236` |
| `curl https://api.parallel.ai` | HTTP 401 за 0,59 с, локальный адрес `172.19.0.1` |
| `curl https://yandex.ru` на `77.88.44.55` и на `5.255.255.77` | таймаут 6 с, локальный адрес пустой |

Два адреса `yandex.ru` уже шли через Ethernet. `ya.ru` в ту же минуту открылся через другой адрес того же оператора. Таймаут этих двух адресов похож на отсутствие ответа хоста, не на повторный заход в `throne-tun`.

## Чего не делать

Подписку ради этого не обновлять. TUN в конце процедуры включён: исключение ставится при пересборке inbound. `netsh winsock reset` — отдельный шаг оператора и крайняя мера; в [#1365](https://github.com/throneproj/Throne/issues/1365) его применяли на другой машине. На профиль с process rules Tun Routing не включать.
